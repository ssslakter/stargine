# Stargine examples

Each directory here is a standalone program that uses the engine as a library.
They double as the engine's own dogfooding: if something is awkward to write in
an example, it is awkward in the API.

## Running them

```bash
pixi run assets              # once, to generate the procedural textures
pixi run example cube
pixi run example solar_system
pixi run example wave_field
```

`pixi run example` with no name lists what is available. Every example needs a
real display; under a compositor that SDL guesses wrong, set the backend
explicitly, e.g. `SDL_VIDEODRIVER=wayland pixi run example cube`.

Controls are the same everywhere: **WASD** to move, **space** and **left shift**
for up and down, the mouse to look, **F11** for fullscreen, **Esc** to quit.

## The examples

### `cube` — the basics

<img src="cube/preview.png" alt="A lit wooden crate" width="420">

A textured crate lit by a point light and a directional light, with the point
light's position drawn as a small white cube that shares its `Transform`. The
arrow keys spin the crate through a ~15 line `EventHandler` defined in the
example, which is the shortest way to see how input extends the engine.

Covers: `Window`, `OpenGLContext`, `Camera`, `basic_material`, `PointLight`,
`DirectionalLight`, `ControlsHandler`, writing your own `EventHandler`.

### `solar_system` — spheres, orbits and a skybox

<img src="solar_system/preview.png" alt="A star, three planets and a moon against a star field" width="420">

A star with three worlds and a moon, wrapped in a cube-map star field. The
planets are indexed sphere meshes; their textures are generated by
`assets/generate.py` from value noise.

Covers: `sphere`, indexed meshes, `CubeMap` and `Skybox`, `texture_material`
for the unlit star, point-light attenuation, `Camera.look_at`.

### `wave_field` — a custom shader

<img src="wave_field/preview.png" alt="A rippling grid surface with a sphere floating above it" width="420">

A 192x192 plane displaced in a hand-written vertex shader, with normals from
central differences so the surface shades itself. The sphere floating above it
recomputes the same wave function on the CPU.

Covers: `plane` with subdivisions, `custom_material` with your own `.glsl`,
per-frame uniforms, texture wrapping and mip filtering.

## What these examples make obvious

Writing them surfaced the engine's current rough edges, in rough order of how
often they got in the way:

- **No transform hierarchy.** `solar_system` has to place the moon by reading
  its planet's world position and adding an offset by hand. A `Transform` with
  a parent would remove that.
- **No CPU access to shader-side geometry.** `wave_field` duplicates its wave
  function in Mojo and in GLSL so the sphere can ride the surface.
- **`view` and `projection` are per-object uniforms.** Every model uploads both
  every frame even though they are the same for the whole frame.
- **Engine assets are found through `$ROOT_DIR`.** The examples only work
  because the runner script sets it; a library should not need that.
- **Values die at their last use**, so every example ends with `_ = context^`
  and `_ = window^` to keep the GL context alive until the resources above it
  are gone. Forgetting either one is a crash at exit, not a compile error.
